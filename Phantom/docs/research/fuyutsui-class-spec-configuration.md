本文回答“Fuyutsui 每个职业、天赋、专精涉及哪些配置”。权威快照为 Fuyutsui commit `60471a59c4160a842011c21226fa62eb8827f91b`，TOC 版本 `1.2.2.4`（`Fuyutsui.toc:1-5`）。TOC 实际加载 13 个 `class/*.lua` 文件（`Fuyutsui.toc:38-50`），本文覆盖其中全部 40 个专精槽：12 个三专精职业，加上德鲁伊的第 4 专精。

证据分为三类，全文不混用：

- **源码事实**：固定 commit 中 Lua/TOC 的直接声明或消费者行为。
- **README 声称**：README 支持矩阵的 ✅（手写逻辑）、🔄（官方一键辅助）、❌（不支持）；它是项目自述，不是静态配置或运行正确性的证明（`README.md:34-60`）。
- **静态推断**：根据声明与消费者的对应关系作出的保守判断；必须在 WoW 中验证，不能据此断言实际支持、法术 ID 有效或外部读取端行为正确。

## 2. 配置模型

### 2.1 `ClassBlocks` 与固定块

职业文件按玩家职业短路，只让当前职业设置 `Fuyutsui.ClassBlocks` 和 `Fuyutsui.MacrosList`（各 `class/*.lua:1-3`）。专精以游戏返回的 `specIndex`（1、2、3；德鲁伊还有 4）选表，而不是以 spec ID 直接选表（`main.lua:374-385`）。

`loadPlayerBlocks` 每次先注入 8 个固定块：`1 锚点`、`2 职业`、`3 专精`、`4 队伍类型`、`5 英雄天赋`、`6 有效性`、`7 一键辅助`、`8 法术失败`，再读取当前专精表（`main.lua:277-354`）。因此下文 B/A/S/G/C 只统计职业文件中的声明，不把这 8 个运行时固定块计入 B；即使唤魔师恩护表为空，加载后仍会有这 8 个固定状态映射。

记号如下：

- **B (`block`)**：职业表中的数字键就是该状态的主色块直接索引，`name` 再被加载为“名称 → 该直接索引”的映射；只有任一源码写入路径使用该名称时才会变化。普通状态主要由 `main.lua` 写入，爆发、AOE、输出模式、延迟和爆发药水等设置切换也可由 `core/core.lua` 写入（`main.lua:408-1315`; `core/core.lua:123-189`）。它不是从表内排列顺序推导的序号。
- **A (`aura`)**：逻辑光环输出，指定 `auraName` 与 `showKey`（通常为 `remaining`、`count` 或 `isIcon`）。消费者按键读取职业光环状态机（`main.lua:319-320`; `core/auras.lua:1452-1473`）。
- **S (`spell`)**：候选法术冷却输出。相同 spell ID 可有普通冷却索引和 `charge=true` 的充能索引；`forcedKnown`、`inSpellBook` 是非默认已知性标志（`main.lua:321-339`）。
- **G (`group`)**：一个起始索引和每成员槽宽，支持生命、职责、驱散、玩家施加的光环及德鲁伊回春计数（`main.lua:340-351,1317-1362,1430-1499`）。
- **C (`countBars`)**：独立计数条声明，`valueType` 仅支持 `castCount` 或 `charge`，并带 `minValue`、`maxValue`、`spellId`（`core/block.lua:73-163`）。

当前像素实现实际创建 510 个主色块：1..255 使用第一套 RGB 编码，256..510 使用第二套编码（`core/block.lua:4-11,34-71`）。职业表中 B/A/S/G 的直接声明键最高为 72；G 的成员展开索引则可能超过 255。

G 的实际成员索引公式是 `start + (memberIndex - 1) * num + offset`；声明键 `start` 自身不是第一个成员字段，`offset` 通常从 1 开始（`main.lua:1320,1343,1476,1495`）。按源码中实际 G 配置，常见范围如下：

| G 配置 | 5 人时实际索引 | 40 人时实际索引 | 第二编码段使用情况 |
| --- | --- | --- | --- |
| `start=70,num=3` | 71..85 | 71..190 | 不使用 256..510 |
| `start=70,num=5` | 71..95 | 71..270 | 第 38..40 名成员会使用 256..270 |
| `start=70,num=6` | 71..100 | 71..310 | 第 31 名成员末格及第 32..40 名成员会使用 256..310 |
| `start=45,num=7` | 46..80 | 46..325 | 第 31..40 名成员会使用 256..325 |

`updateGroup` 会重建/重填队伍状态，但不会先把已离队成员先前占用的主色块清零；因此成员数缩减后，离队槽可能保留旧像素。仓库虽定义 `clearGroupBlocks`，但没有调用点，而且它只清理 `start..255`，即使接入也不会清除 G 展开到 256..510 的部分（`main.lua:1502-1543`）。

## 5. 普通天赋：候选法术门控，不是构筑存储

**源码事实**：当前仓库没有 `C_Traits`、活动配置 ID、节点/条目模型、天赋导入字符串解析或推荐 build 表。`PLAYER_TALENT_UPDATE` 只重新加载专精表与队伍状态（`main.lua:1578-1581`）。源码中的实际调用名是 `IsSpellKnown` / `IsSpellInSpellBook`（文件开头分别从 `C_SpellBook.IsSpellKnown` / `C_SpellBook.IsSpellInSpellBook` 建立同名局部别名）。冷却候选集在延迟 1 秒后逐项调用 `IsSpellKnown(spellID)`；只有已知法术才进入刷新集合。若条目有 `inSpellBook=true`，改用 `IsSpellInSpellBook`；若 `forcedKnown=true`，即使检查失败也保留。未知分支只把该 spell ID 的普通冷却 `index` 写为 1，不会写关联的 `charge` 索引，因此充能像素可能保持 0 或旧值（`main.lua:18-19,165-181,325-338`）。

两个显式例外是：

- 暗影牧师虚空齐射 1242173：`forcedKnown=true`（`class/Priest.lua:154`）。
- 恢复萨满涌动图腾 444995：`inSpellBook=true`（`class/Shaman.lua:150`）。

此外，驱散能力也以 `IsSpellKnown` 对候选 ID 集做动态检查（`main.lua:140-163,188-235`）。因此可准确描述为：**普通天赋影响已声明候选法术是否参与输出；Fuyutsui 不保存一套普通天赋节点、build、导入字符串或 Wowhead 配置。** README 的“脚本使用的天赋均来自 WOWHEAD 推荐天赋”只是 README 声称（`README.md:37-40`），固定 commit 中没有对应构筑数据可验证。

## 7. 直接相关的共享配置

### 7.1 法术输出映射

`Fuyutsui.spellsList` 是共享的“施法/一键辅助/失败法术 → 小整数”映射：一键辅助把 `C_AssistedCombat.GetNextCastSpell()` 查得的 `.index` 写入固定块 7；施法技能块也使用同表；带 `failed=true` 的条目可写固定块 8（`core/config.lua:3-624`; `main.lua:576-612,743-760`）。这张表按职业分段，但不是 `ClassBlocks` 的冷却声明：同一 spell ID 可以同时参与共享技能编号和某专精的冷却输出，也可能只存在其中一侧。

### 7.2 光环状态机

`core/auras.lua` 按职业 ID 保存逻辑光环元数据，并把 `addAuras`、`updateAuras`、`removeAuras` 反向索引到事件和 spell ID。支持冷却、施法成功、图标改变、法术覆盖、屏幕提示和图标发光事件；`step` 更新层数，`castBar` 可要求读条，`overrideSpellID` 用于替代图标，`duration` 控制逻辑过期时间（`core/auras.lua:6-25,27-1149,1151-1420`）。每帧维护剩余时间/层数，再按 A 条目的 `showKey` 输出（`core/auras.lua:1422-1473`）。

### 7.3 专精距离与能量

`rangeSpecID` 为所有 40 个正式专精 ID 及初始专精 ID 指定 10/15/25/30/46 码阈值，供目标距离和范围内敌人数使用（`core/config.lua:788-856`; `main.lua:374-380,1102-1120,1255-1285`）。`EnumPowerType` 声明 WoW power 枚举，`powerNameMap` 再把类型转换成中文 B 名称；运行时遍历所有 power type，但只在当前专精存在同名 B 时写出（`core/config.lua:765-787`; `main.lua:530-574`）。因此职业表中的资源名称是协议的一部分，名称不匹配就不会得到该资源输出。

### 7.4 队伍光环白名单

`Fuyutsui.noSecretAuras` 列出恩护/增辉唤魔师、恢复德鲁伊、戒律/神圣牧师、织雾武僧、恢复萨满、神圣圣骑士的一组光环 ID（`core/config.lua:857-902`）。但在此 commit 的非 vendored Lua 中，名称只出现于该声明，没有消费者引用。队伍光环当前实际通过 `GetAuraDataByIndex` 收集 `sourceUnit == "player"` 且 spell ID 非 secret 的光环，再按 G 的 `auras` 表匹配（`main.lua:1430-1457`）。所以白名单的预期用途可以描述，不能声称它当前生效。

### 7.5 角色设置

角色级默认设置是 `aoeMode=0`、`cooldowns=0`、`dpsMode=0`、`delay=0`、`potion=0`，另含快捷按钮位置/显示；配置保存在 `FuyutsuiADB` 的 `db.char`（`core/core.lua:7-10,388-403`）。专精只有声明对应 B 时才输出爆发、AOE、输出模式和爆发药水；`delay` 由独立切换函数处理（`main.lua:763-779`; `core/core.lua:98-195,223-307`）。

## 9. 结论

固定快照中共有 13 个职业文件和 40 个专精槽，全部有显式表；唯一完全空的专精表是唤魔师恩护。配置的核心不是“保存一套天赋”，而是：按专精选择状态/光环/法术/队伍/计数条声明，按普通天赋已知性筛选候选法术，再结合当前职业上下文解释扁平英雄标记表写出的编码。宏则按职业共享，只有宏文本本身通过 `[spec:]`、`[known:]` 或姿态条件进一步分流。

因此，判断“涉及哪些配置”应同时看三层：README 的支持声称、`ClassBlocks`/宏的静态覆盖、以及共享消费者是否真的读取这些字段。本文前两层已完整盘点，第三层只给出可由源码证明的行为和需运行时复核的差异。
